### WO-051 — Scheduled cleanup job for stale dev cache keys

A scheduled background job must be implemented to purge stale skill:dev:* Redis keys whose embedded SHA no longer matches the current dev branch HEAD SHA, running on a 24-hour cycle as a defense-in-depth supplement to the existing 24-hour TTL on dev cache keys. This job should be implemented in a new file such as src/cache/dev-cache-cleanup.ts, integrated with the Cache Manager module (src/cache/cache-manager.ts) that manages Redis key operations using ioredis. The architecture risk register explicitly identifies dev branch cache pollution as a concern: frequent pushes to dev create SHA-scoped keys (skill:dev:<name>:<version>:<sha>) that accumulate and grow Redis memory usage, even though individual keys have a 24-hour TTL. The cleanup job provides proactive eviction of superseded-SHA keys well before their TTL expires, bounding Redis memory growth during high-churn development periods. When complete, the job will run every 24 hours, scan all skill:dev:* keys, compare each key's SHA segment against the current-sha:dev value in Redis, delete keys with non-matching SHAs, and log the count of purged keys and estimated memory reclaimed via the Pino structured logger. The job must use the same Redis leader-lock pattern as the Poller (SETNX with TTL) to prevent concurrent execution across multiple replicas. This story does not cover main branch cache keys (which are immutable and have no TTL) or index:dev:* keys (which are replaced atomically on SHA change). It depends on the Cache Manager module and the Poller's leader election pattern being implemented first.
